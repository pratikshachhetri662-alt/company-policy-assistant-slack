Rules-based search is the most predictable baseline because it ranks policy records and returns their text directly; it is generally fast and has low risk of adding unsupported rules, but it can miss questions phrased differently from the policy wording. An LLM without a vector index can interpret natural-language questions, but supplying all 98 records creates a larger context, consumes more tokens, and exposes the model to irrelevant policies; it may still invent details that the database does not support. The comparison website reports per-request response time and estimated token use, while labeling unsupported-answer tendency as a qualitative design risk rather than a measured hallucination rate.

The preferred approach is an LLM with a vector index because retrieval narrows the context to the most relevant policy records before generation, making the answer easier to audit and usually reducing irrelevant context and token use compared with passing the entire database. Each response should name the policy title and show its source text, and the bot should explicitly abstain when no relevant policy is found. Retrieval does not guarantee correctness, so the system should be evaluated on a fixed set of in-scope and out-of-scope questions by manually checking whether every answer is supported by the CSV; production use should preserve source references and monitor unsupported answers.
